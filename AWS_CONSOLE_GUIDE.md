# AWS Management Console Navigation & Verification Guide

This guide provides a step-by-step walkthrough of how to locate, inspect, and verify the resources deployed for the **Order Processing System** within the AWS Management Console. 

---

## 🗺️ Quick Architecture Mapping

Here is where each component of our architecture lives in the AWS Console:

| Local Concept / Code Reference | AWS Service | Console Search Term | Key Focus Area |
| :--- | :--- | :--- | :--- |
| **Network Isolation** | VPC | `VPC` | Subnets, Route Tables, NAT Gateway |
| **Compute Cluster** | EKS | `EKS` | Nodes, Pods, OIDC Configuration |
| **Database** | RDS | `RDS` | Databases, Security Groups, Connectivity |
| **Secret & Config Management** | Systems Manager | `SSM` | Parameter Store, SecureStrings |
| **Encryption Keys** | KMS | `KMS` | Key Policies, Aliases |

| **Fine-Grained Security** | IAM | `IAM` | Roles, Trust Relationships, IRSA |
| **Dead-Letter Queue Alerts** | CloudWatch | `CloudWatch` | Metric Alarms, SQS Metrics |

## 1. Networking Infrastructure (Amazon VPC)

The baseline network hosts our EKS nodes and RDS database securely, isolating them from public ingress while allowing secure outbound routing.

### Step-by-Step Walkthrough:
1. Open the AWS Console and search for **VPC**.
2. Click on **Your VPCs** in the left sidebar.
3. Select `ops-sandbox-vpc`.

### Settings & Configurations to Verify:
* **Subnets (6 Total)**:
  * In the left sidebar, click **Subnets**. Filter by `ops-sandbox-vpc`.
  * Verify you have:
    * **3 Public Subnets** (assigned to Route Tables with a `0.0.0.0/0` route to the **Internet Gateway**).
    * **3 Private Subnets** (assigned to Route Tables routing through the **NAT Gateway**).
* **NAT Gateway**:
  * Click **NAT Gateways** in the sidebar. Verify `ops-sandbox-vpc-public-...` is present and **Available**. This NAT Gateway allows EKS pods in private subnets to reach external resource registries (like GHCR).
* **Security Groups**:
  * Click **Security Groups** in the sidebar.
  * Find `ops-sandbox-rds-sg`. Inspect the **Inbound Rules**. It should allow ingress on PostgreSQL port `5432` only from the EKS nodes security group (`ops-sandbox-node-sg`), enforcing network-level database protection.

## 2. Kubernetes Orchestrator (Amazon EKS)

The cluster handles microservice container deployments, service networking, and autoscaling.

### Step-by-Step Walkthrough:
1. Search for **Elastic Kubernetes Service** (EKS).
2. Click **Clusters** in the left sidebar and select `ops-sandbox`.

### Settings & Configurations to Verify:
* **Status**: Should be **Active**.
* **OIDC Provider (Critical for Security)**:
  * Under the **Overview** tab, locate **OpenID Connect provider URL** (e.g., `oidc.eks.us-east-1.amazonaws.com/id/...`).
  * *What it does*: This URL is registered in IAM. It enables AWS to trust authentication tokens generated by Kubernetes service accounts (IRSA).
* **Compute (Managed Nodes & Karpenter)**:
  * Select the **Compute** tab.
  * Verify the node group named **primary**. This is the static EKS node group running the base controllers.
  * Any nodes named with a prefix like `ip-10-0-x-x` (which are not in the `primary` node group) were dynamically provisioned by **Karpenter** in response to scheduling demands.
* **Resources (Pods & Controllers)**:
  * Select the **Resources** tab.
  * Under **Pods** (in namespace `default`), you should see your running microservices (e.g., `order-service-...`, `payment-service-...`).
  * Under **Custom resources**, you can inspect Karpenter's configurations by clicking `karpenter.sh/v1/NodePool` or `karpenter.k8s.aws/v1/EC2NodeClass`.

## 3. Relational Storage (Amazon RDS)

Our PostgreSQL database stores persistent relational records (orders and outbox event tables).

### Step-by-Step Walkthrough:
1. Search for **RDS**.
2. Click **Databases** in the left sidebar and select `ops-sandbox-db`.

### Settings & Configurations to Verify:
* **Endpoint & Port**:
  * Under **Connectivity & security**, note the **Endpoint** domain name. This is the host address that the microservices use to connect.
* **Encryption**:
  * Select the **Configuration** tab.
  * Verify **Storage encrypted** is `Yes` and the Master Key points to your KMS Key (`alias/ops-sandbox-ssm`).
* **Performance Insights**:
  * Select the **Monitoring** tab. You can view real-time DB CPU load, active sessions, and write operations here.

---

## 4. Secure Configuration (AWS Systems Manager Parameter Store)

SSM holds database connection strings encrypted at rest. Pods decrypt these on startup.

### Step-by-Step Walkthrough:
1. Search for **Systems Manager**.
2. Click **Parameter Store** in the left sidebar (under *Application Management*).

### Settings & Configurations to Verify:
* **Parameters**:
  * Verify `/ops-sandbox/order-service/DATABASE_URL` and `/ops-sandbox/inventory-service/DATABASE_URL` exist.
* **Type & Key**:
  * Click on `/ops-sandbox/order-service/DATABASE_URL`.
  * **Type** should be `SecureString`.
  * **KMS Key ID** should be `arn:aws:kms:us-east-1:...:key/...` (aliased to `alias/ops-sandbox-ssm`).
  * Select **Show decrypted value** to inspect the parsed connection string containing the host endpoint and random database password.

## 5. Encryption Key Management (AWS KMS)

KMS manages the Customer Managed Key (CMK) that encrypts our SSM parameters, RDS storage, and SQS messages.

### Step-by-Step Walkthrough:
1. Search for **KMS** (Key Management Service).
2. Click **Customer managed keys** in the left sidebar.
3. Look for the key with the Alias name `alias/ops-sandbox-ssm`.

### Settings & Configurations to Verify:
* **Key Policy (Cryptographic Boundary)**:
  * Scroll down to the **Key policy** tab.
  * *What it does*: It defines which IAM principals can decrypt information using this key. Look for statements allowing:
    * The root account to administer the key.
    * The platform's ESO IAM role (`ops-sandbox-eso-role`) to perform `kms:Decrypt` actions.
    * The SQS/SNS services to generate data keys for encrypting/decrypting messages.

## 6. Message Queues & Topics (Amazon SQS & SNS)

SQS and SNS handle asynchronous communication between microservices, ensuring loose coupling and high reliability.

### Step-by-Step Walkthrough (SNS):
1. Search for **Simple Notification Service** (SNS).
2. Click **Topics** and select `ops-sandbox-payment-processed-topic`.
3. Under **Subscriptions**, you should see three entries pointing to SQS endpoints:
   * `ops-sandbox-payment-processed-analytics`
   * `ops-sandbox-payment-processed-inventory`
   * `ops-sandbox-payment-processed-notification`
   * *What it does*: When a message is published to the SNS topic, SNS automatically "fans out" a copy of that message to all three SQS queues simultaneously.

### Step-by-Step Walkthrough (SQS):
1. Search for **Simple Queue Service** (SQS).
2. Filter the queue list by `ops-sandbox-`.

### Settings & Configurations to Verify:
* **Dead-Letter Queues (DLQ)**:
  * Select `ops-sandbox-payment-processed-notification`.
  * Under the **Dead-letter queue** tab, verify it lists `ops-sandbox-payment-processed-notification-dlq` as its target.
  * **Maximum receives** should be `3`. (If a consumer fails to process a message 3 times, SQS isolates it by pushing it to the DLQ).
* **Encryption**:
  * Verify **Encryption** is `Enabled` and configured with KMS (using `alias/ops-sandbox-ssm`). This guarantees that messages in flight and at rest in the queues are secure.

## 7. Security Roles (AWS IAM)

IAM roles permit Kubernetes service accounts to securely communicate with AWS resources without using static credentials.

### Step-by-Step Walkthrough:
1. Search for **IAM**.
2. Click **Roles** in the left sidebar and search for `ops-sandbox-order-service-role`.

### Settings & Configurations to Verify:
* **Trust Relationships**:
  * Click the **Trust relationships** tab.
  * Inspect the policy. It must trust the EKS OIDC provider and contain a condition statement mapping:
    * `system:serviceaccount:default:order-service`
    * `system:serviceaccount:default:outbox-relay`
  * *What it does*: This trust relationship allows EKS to issue temporary credentials to these specific pods, allowing them to assume the role.
* **Permissions Policies**:
  * Select the **Permissions** tab.
  * Verify the policy `ops-sandbox-order-service-policy` is attached.
  * Click on the policy to verify it only permits SQS actions (`sqs:SendMessage`) to the `ops-sandbox-order-pending` queue, enforcing the Principle of Least Privilege.

## 8. Monitoring & Alerts (Amazon CloudWatch)

CloudWatch alarms notify administrators of message failures in Dead-Letter Queues.

### Step-by-Step Walkthrough:
1. Search for **CloudWatch**.
2. Click **All Alarms** under *Alarms* in the left sidebar.

### Settings & Configurations to Verify:
* **DLQ Alarms**:
  * Look for the alarm named `ops-sandbox-payment-notification-dlq-non-empty` (or similar).
  * **State**: Should be `OK` (or `Insufficient Data` if no messages have ever gone to the DLQ).
  * **Conditions**: Triggers when `ApproximateNumberOfMessagesVisible` is `> 0` for `1` datapoint in `1 minute`.
  * *What it does*: Instantly triggers if a message fails processing multiple times and ends up in the DLQ, alerting SREs of code or integration failures.
